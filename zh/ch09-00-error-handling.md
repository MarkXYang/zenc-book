# 错误处理

错误是软件工程中无法避免的现实。磁盘空间会耗尽、网络连接会断开、配置文件可能包含语法错误，不受信任的客户端也可能传入无效输入。一门编程语言处理错误的方式直接影响其软件的可靠性、可维护性和安全性。

在传统 C 语言中，错误处理严重依赖零散的约定：
- **哨兵返回值**：返回 `-1`、`0` 或 `NULL` 表示失败。如果调用者忘记检查返回码，无效数据就会未经校验直接进入后续计算，往往导致静默数据损坏或灾难性崩溃。
- **全局状态（`errno`）**：在发生失败后检查线程局部整数标志，这极易被忽略，且容易被后续的库调用覆盖。
- **`goto cleanup` 阶梯**：手动跳转跳过故障点以释放资源，这会产生脆弱的代码，漏掉一个标签就会导致内存泄漏或双重释放。

像 C++ 和 Java 这样的现代高级语言引入了**异常**（`try`/`catch`/`throw`）。虽然异常自动化了错误传播，但它们带来了不确定的运行时开销、引入了隐式控制流路径、使析构器展开变得复杂，并且在嵌入式、内核和关键安全领域中是被禁止的。

Zen C 采用了一种现代系统级方法：**显式、类型安全且零成本的错误处理**。

---

## Zen C 的哲学：可恢复错误与不可恢复错误

Zen C 将错误划分为两个不同的类别：

1. **不可恢复错误（`panic`）**：
   这些代表灾难性故障或不变量违背，此时程序无法有意义地继续执行——例如内部损坏、不可能的状态转换或契约违背。Zen C 使用 **`panic`** 处理不可恢复错误，它会打印诊断详情并立即中止执行。

2. **可恢复错误（`Result<T>` 与 `Option<T>`）**：
   这些代表编写良好的应用程序能够预料并优雅处理的预期情况——例如文件无法打开、网络超时或可选值不存在。Zen C 使用标准的 **`Result<T>`** 和 **`Option<T>`** 类型对这些情况进行建模，并配合简洁的 **`?`** 尝试运算符。

Zen C 没有隐式的异常运行时或动态栈展开表。每个错误路径都是显式类型化的，在函数签名中清晰可见，并直接转译为高效、可预测的 GNU C11 分支。
